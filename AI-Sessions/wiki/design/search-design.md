# Search Design

> **구현 시기: 10월.** 9월 범위(발주 한 줄기)에 포함되지 않는다.
> 실작업 11일에 데이터 작업까지 넣으면 둘 다 껍데기가 되어 이월했다.
> 작업 문서는 [[oct-law-rag]], [[oct-web-fallback]].

## Summary

검색은 **계단식**이다. 위에서부터 내려가며 답이 나오면 멈춘다.
모든 답변에는 출처 배지가 붙고, 답할 데이터가 없으면 지어내지 않고 대체 지표로 치환한다.

데이터 성격에 따라 경로가 갈린다 — 비정형 문장은 벡터, 정형 행은 SQL.

## Context

기획 원안은 "규제 시맨틱 검색(RAG)" 하나였으나, 실제로는 세 종류의 질문이 섞여 들어온다.

| 질문 | 필요한 연산 |
|---|---|
| "테라스 영업 불법인가요?" | 의미 유사도 → 벡터 |
| "역삼동 카페 몇 개야?" | 개수 집계 → SQL |
| "어제처럼 발주해줘" | 날짜 범위 조회 → SQL |

정형 데이터를 임베딩하면 집계·범위·좌표 계산이 구조적으로 불가능해진다.
벡터 검색은 "상위 N개 유사한 것"만 돌려주므로 `count(*)`를 대신할 수 없다.

## Details

### 검색 계단

| 순서 | 경로 | 배지 | 속도 |
|---|---|---|---|
| ① | 칩 버튼 (사전 작성 답변) | 🟢 검증됨 | 즉시 |
| ② | `qa_cache` (질문 해시 일치) | 원본 배지 유지 | 5ms |
| ③ | `stores` SQL 집계 | 🔵 공공데이터 | 1~10ms |
| ④ | `law_chunks` 벡터 검색 | 🟢 조문 번호 | 1.5초 |
| ⑤ | `user_knowledge` (본인 것만) | 🔴 미확인 | 1.5초 |
| ⑥ | 웹 폴백 (웹 검색 + LLM) | 🔴 미확인 | 2~4초 |

**웹 폴백**은 ①~⑤에서 답이 없을 때만 쓰는 마지막 수단이다. LLM이 웹을 훑어 정리하는
과정에서 옛 정보를 가져오거나 없는 내용을 지어낼 수 있는데, 화면상으로는 검증된 답변과
똑같이 그럴듯해 보인다. 그래서 "저희가 확인한 게 아닙니다"를 배지로 눈에 보이게 한다.

웹 폴백 결과는 `user_knowledge`에 **본인 전용으로** 저장한다([[data-isolation-policy]]).

### 집계 불가 판정

상권 API가 주는 것은 **"현재 영업 중인 업소 스냅샷"**이다. 시계열이 아니다.
따라서 "카페 폐업률"처럼 작년과 올해를 비교해야 나오는 값은 계산할 수 없다.

| 유형 | 예시 | 처리 |
|---|---|---|
| 집계 가능 | "역삼동 카페 몇 개?" | SQL → 숫자 그대로 |
| **집계 불가** | **"카페 폐업률?"** | **한계 고지 + 계산되는 지표로 치환** |

치환 응답:

```
"폐업률은 저희 데이터로 계산할 수 없습니다. 대신 말씀드릴 수 있는 것:
  · 역삼동 커피전문점 1,842개 (전체 업소의 8.3%)
  · 반경 500m 내 경쟁 카페 23개
  · 동일 업종 밀집도 상위 12%"
```

판정은 **집계 가능 지표 화이트리스트**(`lib/search/whitelist.ts`)로 한다.
목록에 없으면 자동으로 "집계 불가"다. LLM 의도 분류에 맡기면 없는 데이터를 있다고
분류하는 순간 뚫린다.

시계열이 필요하면 통계청·공공데이터포털의 생존율 통계를 **별도로 받아** 넣어야 한다.

### SQL 생성 금지

**LLM에게 SQL 문자열을 생성시키지 않는다.** 미리 만든 쿼리 3~4개(개수, 목록, 반경)에
값만 파라미터로 꽂는다. 자유 SQL 생성은 인젝션 경로다.

```
"역삼동에 카페 몇 개야?"
      ↓ LLM (조건 추출만)
{ 지역: "역삼동", 업종: "커피전문점", 집계: "count" }
      ↓ 정해진 쿼리에 값만 끼움
select count(*) from stores where category = $1 and address like $2
      ↓ 1842 → 화면에 그대로 렌더 (뒷단 LLM 생략)
```

### 속도 설계

병목은 SQL이 아니라 LLM이다(호출당 0.3~1.5초). 벡터 검색을 써도 임베딩 호출이
하나 더 붙을 뿐 사정은 같다. 그래서 **LLM을 부르지 않는 경로를 먼저 탄다.**

- 캐시는 **문자열 해시**로 시작한다. 시맨틱 캐시는 적중률이 실제로 부족할 때만 —
  법률 도메인에서 유사도 캐시는 오답을 퍼뜨릴 위험이 있다
- 결과가 표·숫자면 **뒷단 LLM을 생략**하고 그대로 렌더한다(1.5초 절약, 가독성도 낫다)
- 법령 답변처럼 LLM 문장이 꼭 필요한 곳은 **스트리밍**. 총 시간은 같아도 첫 글자가
  0.5초에 나오면 빠르다고 느낀다
- "어제 발주 보여줘"는 정규식으로 잡아 LLM을 아예 건너뛴다

**"빅데이터를 학습시키면 빨라진다"는 성립하지 않는다.** 임베딩·색인은 *찾을 수 있게*
만드는 것이지 *빠르게* 만드는 것이 아니다.

### 벡터 검색 쿼리

```sql
select law_name, article, content
  from law_chunks
 order by embedding <=> $1
 limit 5
```

유사도 임계값 미달이면 ⑤로 내려간다. 임계값은 실제 데이터를 넣고 조정한다.

### 법률 리스크 방어 (타협 불가)

- 모든 답변에 "참고용, 법적 효력 없음" 고지
- 출처 조문 원문을 항상 함께 노출
- 근거가 없으면 비워두고 "확인 필요" — 지어낸 값이 앱에 들어가는 것이 가장 위험하다

### 테스트 방법

1. 조문에 있는 질문 3개 → 🟢 배지
2. 조문에 없는 질문 3개 → 🔴 배지
3. "역삼동 카페 몇 개?" → 숫자
4. "카페 폐업률?" → **치환 응답**. 숫자가 나오면 실패다(지어낸 값이라는 뜻)

화이트리스트 분류는 `assert` 기반 자체 점검을 남긴다.
