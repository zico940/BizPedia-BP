# Order Design

## Summary

발주 도메인의 설계다. **9월 범위의 전부**이자 이 제품에서 매일 쓰이는 유일한 기능이다.

자연어("내일 대파 2단 김사장님께 주문해")를 거래처에 보낼 정형 텍스트로 바꾸고,
과거 발주를 불러와 재사용한다. **어느 경로든 사장님 승인 없이 발주가 나가지 않는다.**

## Context

발주는 경쟁이 포화된 영역이다(푸드팡·마켓보로 등). 그럼에도 9월 범위를 발주에 올인하는
이유는 **매일 쓰는 유일한 기능**이기 때문이다. 과태료 체크리스트는 1년에 3번 쓰므로
2주로는 재방문을 관찰할 수 없다.

검증 기준도 여기에 걸려 있다 — 사장님 10명 중 **3명이 일주일 뒤에도 쓰는지.**

## Details

### 전체 흐름

```
[입력]  텍스트 또는 음성
   ↓
[분기]  정규식으로 "어제처럼" 류인지 판정
   ├ 재사용  → 날짜 파싱 → SQL 조회 → 확인 리스트
   └ 신규    → LLM 변환 → 거래처 매칭 → 확인 화면
   ↓
[승인]  사장님이 확인 버튼을 누른다  ← 생략 불가
   ↓
[저장]  orders 저장
   ↓
[공유]  OS 공유 시트 → 카카오톡
```

### 1. 발주 텍스트 변환

LLM에게 **문장 생성이 아니라 구조 추출**을 시킨다. 문구 조립은 코드가 한다.
그래야 출력이 흔들리지 않고 zod로 검증할 수 있다.

추출할 구조:

```ts
{
  vendor_hint: string,       // "김사장" — 매칭 전 원문 그대로
  items: [
    { name: string, qty: number, unit: string }
  ],
  deliver_on: string | null  // "내일" → ISO 날짜. 없으면 null
}
```

**LLM 응답은 반드시 zod로 검증한다.** 형식이 깨지면 재시도하고, 두 번 실패하면
사장님에게 직접 입력을 요청한다. 깨진 응답을 그대로 쓰지 않는다.

문구 조립은 템플릿이다:

```
[매장명] 발주
- 대파 2단
- 양파 1망
납품: 9월 17일
```

### 2. 거래처명 매칭 — 실제 난관

"김사장"은 여러 명일 수 있고, 별칭·오타·경칭이 섞인다. 판정 순서:

| 순서 | 조건 | 처리 |
|---|---|---|
| 1 | 정확히 일치 | 확정 |
| 2 | 경칭·공백 제거 후 일치 ("김사장님"→"김사장") | 확정 |
| 3 | 부분 일치가 **1건** | 확정하되 화면에 표시 |
| 4 | 부분 일치가 **2건 이상** | **되묻는다** — 후보를 버튼으로 |
| 5 | 없음 | **되묻는다** — 거래처 등록 유도 |

**추측해서 확정하지 않는다.** 잘못된 거래처로 발주가 나가면 실물 손해다.
4·5번은 실패가 아니라 정상 흐름이다.

```
# ponytail: 문자열 정규화 + 부분 일치. 퍼지 매칭 라이브러리는 오탐이 늘면 그때.
```

### 3. 발주 재사용 — "어제처럼"

**정규식이 먼저, LLM은 폴백이다.** 표현이 뻔해서 대부분 정규식에서 잡히고,
잡히면 LLM을 건너뛰어 0.3초에 끝난다.

정규식이 처리할 표현: `오늘`, `어제`, `그저께`, `N일 전`, `이번 주`, `지난주`, `저번에`

```
"어제처럼 발주해줘"
  ├ 정규식 성공 → 날짜 계산 → SQL
  └ 실패 → LLM에게 날짜 추출 요청 → SQL
       ↓
  where user_id = $1                                  ← 격리
    and created_at >= now() - ($2 || ' days')::interval  ← 범위 경계
       ↓
  확인 리스트 → 승인 → 새 orders 행 (draft → sent)
```

두 가지가 동시에 걸린다:

- `user_id` — 남의 발주가 보이면 개인정보 사고 ([[data-isolation-policy]])
- `ai_range_days` — 설정 범위 밖은 조회되면 안 됨. **세션에서 읽는다.**
  클라이언트가 보낸 값을 쓰지 않는다

과거 발주를 **수정하지 않는다.** 재사용은 항상 새 행을 만든다. 원본이 바뀌면
"어제 뭘 시켰더라"의 답이 사라진다.

### 4. 승인 플로우 (생략 불가)

신규든 재사용이든 **확인 화면을 거친다.**

발주는 `orders.status`로 상태를 갖는다.

| 상태 | 시점 | 의미 |
|---|---|---|
| `draft` | 확인 화면에 올라갈 때 저장 | 아직 안 보냄 |
| `sent` | [보내기]를 누른 뒤 (`sent_at` 기록) | 거래처로 나감 |
| `issue` | 거래처 매칭 실패·모호로 보류 | 사장님 확인 대기 |

**원칙은 "승인 없이 발주가 나가지 않는다"이지 "저장하지 않는다"가 아니다.**
확인 화면 진입 시점에 `draft`로 저장해두면 중단된 발주를 복구할 수 있어 사장님에게 이롭고,
[[aura-export-design]]의 3분류도 이 컬럼으로 채워진다.

```
┌────────────────────────┐
│ 김사장 (청과)           │
│ · 대파 2단              │
│ · 양파 1망              │
│ 납품: 9월 17일          │
│                        │
│ [수정]      [보내기]    │
└────────────────────────┘
```

- LLM이 곧바로 발송하지 않는다
- 매칭이 3번(부분 일치 1건)이었으면 거래처명 옆에 근거를 표시한다
- **[보내기]를 눌러야 `sent`로 바뀌고 공유 시트가 열린다.** 그 전까지는 `draft`다

### 5. 저장과 공유

`orders`에 원문(`raw_input`)과 결과(`result_text`)를 **둘 다** 남긴다.
원문이 있어야 변환 품질을 나중에 점검할 수 있다.

공유는 Web Share API(`navigator.share`). 알림톡은 사업자 검수가 필요해 MVP에서 못 쓴다.
데스크톱 브라우저는 미지원이 있어 **클립보드 복사 폴백**을 둔다.

### 6. 음성 입력

Web Speech API로 공짜다. 다만 **주방 소음에서의 정확도는 별개 문제**라
텍스트 입력을 항상 병행한다. 음성은 편의 기능이지 대체재가 아니다.

## 테스트 방법

`assert` 기반 자체 점검을 남길 대상:

| 대상 | 확인할 것 |
|---|---|
| 거래처명 매칭 | 동명이인 2건 → 되묻기. 경칭 제거 후 일치 → 확정 |
| 날짜 파싱 | "어제"·"3일 전"·"지난주" → 올바른 날짜 |
| 범위 경계 | `ai_range_days=1`에서 10일 전 발주가 **안 나오는지** |

육안 확인:

1. 실제 발주 문장 10개를 넣어 변환 결과 확인
2. "어제처럼 발주해줘" → **승인 전에는 `sent`가 되지 않는지** (`draft`로만 남아야 한다)
3. 계정 두 개로 남의 발주가 보이지 않는지
