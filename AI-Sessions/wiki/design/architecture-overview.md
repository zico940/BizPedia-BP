# BizPedia 아키텍처 정의서 (팀 공유용 요약본)

> **이 문서의 성격**: 지금까지의 기술 설계는 개발자 한 명이 혼자 만든 초안이다.
> 아직 팀 전원이 함께 확정한 것이 아니다. 이 문서는 그 초안을 비개발 직군도 읽을 수 있게
> 풀어써서, **팀 전원이 "이대로 갈지" 합의하는 자리에 올리기 위한 정의서**다.
> 여기 적힌 내용 중 `(미확정)` 표시가 없는 것도 "개발자가 이렇게 정했다"이지 "팀이
> 합의했다"는 뜻은 아니다. 팀 합의로 확정되면 이 문서의 `status`가 바뀐다.

## Summary

BizPedia는 소상공인(가게 사장님)을 위한 **발주 도우미 + 놓치기 쉬운 의무 챙기기 서비스**다.
2026년 9월 30일까지 "발주" 기능 하나로 먼저 실사용자 검증을 받고, 세금·교육·노무 같은
컴플라이언스 기능은 10월에 더한다. 시스템은 화면(웹)과 데이터베이스, 그 사이를 잇는
AI(LLM) 호출로만 이루어진 단순한 구조이고, 사장님이 확인 버튼을 누르기 전에는 아무 것도
밖으로 나가지 않는다는 원칙이 뼈대다.

## Context

다른 팀(Team A)의 프로젝트 정의서·아키텍처 정의서 형식을 참고해, 우리 프로젝트도 팀 전체가
공유할 수 있는 한 장짜리 아키텍처 정의서를 만들어 달라는 요청으로 시작했다. 다만 Team A
문서 원본(`AI-Sessions/raw/[프로젝트A]시스템 아키텍쳐 정의서.pdf`,
`AI-Sessions/raw/Team A 프로젝트 정의서_v1.docx`)은 이번에 열람 도구가 준비되지 않아
내용을 그대로 참고하지 못했다. **이 문서는 BizPedia 자체 설계 문서와
`interview-needs-analysis.md`(소상공인 인터뷰 대비 설계 분석)만을 근거로 작성했다.**

세부 기술 결정은 아래 문서들에 이미 있다. 이 문서는 그 내용을 요약·번역한 것이지 새로운
내용을 추가하지 않는다. 정확한 값이 필요하면 반드시 원본 문서를 확인한다.

## Details

### 1. 이 서비스는 무엇을 하나

사장님이 겪는 문제는 "정보가 없어서"가 아니라 **"내 가게가 제대로 돌아가고 있는지, 뭘
놓치고 있는지 스스로 판단하기 어렵다"**는 것이다 (소상공인 인터뷰 결론).

BizPedia의 답은 두 단계다.

1. **매일 쓰는 이유**: 발주(거래처에 재료 주문 넣기)를 문자 메시지 쓰듯 편하게 하도록
   돕는다. 이게 사장님이 매일 앱을 여는 이유가 된다.
2. **발주가 자동으로 챙겨주는 것**: 발주 기록이 쌓이면, 그 기록을 이용해 세금·교육·노무
   같은 놓치기 쉬운 의무도 자동으로 챙겨줄 수 있다. (이 두 번째 단계는 10월부터 본격
   구현 — 아래 "지금 만드는 것 / 나중에 만드는 것" 참고)

검증 기준(성공의 정의)은 **사장님 10명 중 3명이 일주일 뒤에도 계속 쓰는지**다. 자세한
배경은 [[bizpedia-mvp]] 참고.

### 2. 전체 구조 그림

한 문장으로: **화면(Next.js) 하나가 데이터베이스(Postgres) 하나에 직접 말을 걸고, 필요할
때만 AI(LLM)를 불러 쓰는 구조.** 서버가 여러 개로 쪼개져 있지 않다.

```
[사장님 화면 (웹, 모바일 우선)]
        │
        ▼
[Next.js — 화면과 서버 로직이 한 몸]
        │              │
        ▼              ▼
[Postgres DB]      [AI(LLM) 호출]
 (발주·거래처·      (문장 이해·
  할 일·법령 등)     검색 보조)
```

- 왜 서버를 두 개(예: 화면용 Next.js + 로직용 Python)로 안 쪼갰나 — 서버가 둘이면
  배포·로그인 연동·서로 다른 주소 간 통신(CORS) 처리 비용이 두 배가 된다. 지금 인력·기간으로는
  감당하기 어렵다고 판단했다 ([[tech-stack-selection]]).
- 파이썬은 화면을 서빙하는 서버가 아니라, 법령 문서를 미리 AI가 읽기 좋은 형태(임베딩)로
  가공해두는 **배치 작업**에만 쓴다.
- 데이터베이스는 일반 표(테이블) 데이터와, 법령처럼 "의미로 찾아야 하는" 데이터
  (벡터 검색, pgvector)를 한 데이터베이스 안에 같이 둔다. 별도 검색 전용 서버를 두지
  않는다.
- 로그인은 카카오 소셜 로그인 하나만 쓴다 (표준 인증 라이브러리 Auth.js 사용,
  직접 구현하지 않음) — [[auth-design]].

자세한 표·근거는 [[tech-stack-selection]], 전체 테이블 구조는 [[database-design]] 참고.

### 3. 핵심 흐름 — 발주가 어떻게 나가는가

사장님이 문자처럼 편하게 쓰는 흐름을 지키면서도, **AI가 실수해도 실제 사고로 이어지지
않게** 만든 구조다.

```
사장님이 문장을 입력한다
  ("내일 대파 2단 김사장님께 주문해")
        │
        ▼
AI가 "무엇을, 누구에게, 언제"만 뽑아낸다
  (AI가 직접 문장을 만들어 보내는 게 아니라,
   재료를 뽑으면 정해진 양식에 코드가 끼워 넣는다)
        │
        ▼
거래처 이름이 맞는지 확인한다
  (같은 이름이 여러 명이면 사장님에게 되묻는다 —
   AI가 추측해서 마음대로 정하지 않는다)
        │
        ▼
**사장님이 화면에서 확인하고 [보내기]를 눌러야만**
  실제로 거래처에 전달된다
        │
        ▼
카카오톡 등으로 공유한다
```

- **"승인 없이는 아무 것도 나가지 않는다"**가 이 서비스에서 가장 중요한 원칙이다. AI가
  잘못 이해해도, 사장님이 누르기 전까지는 실제 발주(=돈이 걸린 행동)로 이어지지 않는다.
- 어제 발주와 똑같이 다시 시키고 싶을 때("어제처럼 발주해줘")는 AI를 부르지 않고 규칙
  기반으로 먼저 처리해서 빠르고 저렴하게 만든다.
- 왜 이게 10월 기능(세금·교육 체크리스트 등)보다 먼저인가 — 체크리스트류는 1년에 몇 번만
  쓰이는 기능이라 "매주 계속 쓰는지"를 2주 안에 확인할 방법이 없다. 발주는 매일 쓰는
  행동이라 짧은 기간에도 검증할 수 있다.

자세한 표·예외 처리 규칙은 [[order-design]] 참고.

### 4. 사장님 정보를 어떻게 지키나

한 문장 요약: **모든 데이터 조회는 "이 요청을 보낸 사장님 것만" 걸러서 보여주고, 이 규칙을
코드 한 곳에서만 관리한다.**

- 직접 운영하는 데이터베이스를 쓰기로 하면서, 어떤 도구를 썼다면 자동으로 걸렸을 안전장치
  (RLS)가 자동으로 붙지 않게 됐다. 그래서 "모든 조회에 사용자 확인을 끼워 넣는다"는 규칙을
  코드 리뷰로 사람이 지킨다.
- AI가 예전 발주 기록을 검색할 수 있는 기간(범위)은 사장님이 설정한 값을 **서버가 직접
  읽어서** 적용한다. 화면(브라우저)에서 보내는 값을 그대로 믿지 않는다 — 그러면 값을
  조작해서 정해진 범위 밖 데이터를 볼 수 있게 되기 때문이다.
- 웹에서 긁어온(아직 검증 안 된) 정보는 "모두가 보는 지식"과 완전히 다른 표(테이블)에
  저장해서, 작성한 사장님 본인에게만 보이게 한다. 실수로 표시 여부만 바꾸는 방식이 아니라
  아예 테이블을 나눠서, 한 곳을 빠뜨려도 남의 정보가 새지 않게 만들었다.

이름·전화번호처럼 실제 개인정보를 받는 순간부터 개인정보처리방침이 법적으로 필요하다 —
이 부분은 미루지 않고 바로 만든다. 자세한 근거·검증 방법은 [[data-isolation-policy]] 참고.

### 5. 다른 팀(AURA) 대시보드와는 어떻게 연결되나

BizPedia는 더 큰 프로젝트(AURA)의 한 조각이고, 10월에 다른 팀들과 결과를 한 화면(대시보드)
에 모을 계획이 있다. 이를 위해 **정해진 공통 양식(JSON) 하나로 우리 데이터를 내보내는
어댑터(변환기)**를 따로 만들어둔다.

- 중요한 원칙: **우리 내부 데이터베이스 구조는 바꾸지 않는다.** 공통 양식이 요구하는 이름과
  우리 데이터베이스 안 이름이 달라도, "내보낼 때만" 이름을 바꿔주는 변환기 파일 하나로
  해결한다. 그래야 나중에 공통 양식이 바뀌어도 우리 데이터베이스는 건드리지 않아도 된다.
- **전달 방식(파일로 줄지, API로 받아가게 할지, 데이터베이스를 공유할지)은 아직 다른 팀과
  정해지지 않았다 (미확정)**. 9월에는 "정해진 양식으로 만들어서 내려받을 수 있는 것"까지만
  하고, 실제 연결은 10월에 다른 팀과 맞춘다.

자세한 필드 매핑은 [[aura-export-design]] 참고.

### 6. 지금 만드는 것 / 나중에 만드는 것

| 시기 | 범위 | 왜 |
|---|---|---|
| 9월 (~09-30) | 발주 기능 하나 (입력 → 확인 → 전송 → 재사용) | 매일 쓰는 유일한 기능이라 짧은 기간에도 "계속 쓰는지" 검증 가능 |
| 10월 이후 | 세금·교육·노무 등 의무 체크리스트, 법령 검색(AI에게 법 조항 물어보기), 상권 정보 검색, 영업 중/예비창업자 화면 분기 | 1년에 몇 번만 쓰는 기능이라 짧은 기간으로는 검증이 안 됨. 데이터 준비(법령 수집 등)에도 며칠이 걸림 |

일정이 밀릴 경우 포기하는 순서(우선순위가 낮은 것부터): 다른 팀 대시보드용 내보내기 →
발주 이력 화면(데이터는 계속 쌓이므로 화면만 나중에) → 음성 입력(텍스트 입력이 대신함).
**절대 포기하지 않는 것**: 개인정보 격리, 검색 범위 보안 경계, 발주 전 확인 단계 — 이 셋이
깨지면 개인정보 사고나 실제 오발주 사고로 이어진다.

### 7. 아직 팀이 함께 정해야 할 것 (확인이 필요한 항목)

아래는 개발자 혼자 정할 수 없거나 아직 결정이 안 난 것들이다. 이 문서를 팀 검토에 올리는
가장 큰 이유이기도 하다. 원출처: [[bizpedia-mvp#확인이 필요한 항목]].

| # | 항목 | 왜 팀 합의가 필요한가 |
|---|---|---|
| 1 | AI(LLM) 제공자 (미확정) | 어떤 AI 회사 서비스를 쓸지에 따라 비용·품질이 달라짐. 09-20 전 확정 필요 |
| 2 | 서비스를 올릴 서버 사양·접속 방법·도메인 (미확정) | 인터넷 주소(도메인)가 없으면 카카오 로그인 자체가 막힘. 09-30 전 필요 |
| 3 | 수익 모델 (미확정) | 이 서비스로 어떻게 돈을 벌지가 아직 없음. 9월 범위 밖이지만 제품 방향 자체를 바꿀 수 있는 요소 |
| 4 | 다른 팀(AURA) 대시보드 연동 방식 (미확정) | 파일/API/DB 공유 중 무엇으로 할지 다른 팀과 맞춰야 함 (10월) |
| 5 | 서비스 대상 업종·지역 (미확정) | 법령·상권 데이터를 10월에 준비하려면 범위가 먼저 정해져야 함 |

이 항목들은 개발자가 임의로 정하지 않고, 확정되기 전까지 `(미확정)` 표시를 유지한다.
