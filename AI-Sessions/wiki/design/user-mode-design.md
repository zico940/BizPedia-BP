# User Mode Design

> **구현 시기: 10월.** 화면 분기는 이월했다. 다만 `app_users.status` 컬럼과
> 가입 폼의 "아직 준비 중" 선택지는 **9월에 만든다** — 나중에 마이그레이션을
> 다시 쓰지 않기 위해서다. 작업 문서는 [[oct-checklists]].

## Summary

영업 중인 사장님과 예비창업자를 **`app_users.status` 컬럼 하나**로 구분한다.
별도 화면이나 테이블을 만들지 않는다. 달라지는 것은 홈 화면 구성과 칩 버튼 목록뿐이다.

## Context

타깃을 예비창업자까지 넓히기로 했다. 처음에는 화면도 둘, 데이터도 둘이 되어 10일에
무리라고 봤으나, 설계해 보니 추가 비용이 거의 없었다.

예비창업자에게는 오히려 **상권 검색이 핵심 기능**이 된다. "반경 500m 경쟁업체"는 영업 중인
사장님에겐 이미 아는 정보지만, 창업 준비 중인 사람에겐 핵심 판단 재료다.
이미 만드는 기능의 쓸모가 커지는 셈이다.

검증 측면에서도 유리하다. 사장님 10명을 모으는 것보다 예비창업자를 찾는 편이 쉽고
(창업 카페·지원센터), 이들은 새 도구를 더 적극적으로 쓴다.

## Details

### 상태 값

```sql
status text not null default 'open'
       check (status in ('open', 'preparing'))
```

가입 폼 업종 선택에 **"아직 준비 중(창업 예정)"** 항목을 넣고, 고르면 `preparing`이 된다.
사업자등록 후 설정 화면에서 `open`으로 바꾼다.

### 모드별 차이

| 기능 | `open` (영업 중) | `preparing` (예비창업자) |
|---|---|---|
| 홈 상단 | 과태료 D-Day 체크리스트 | 개업 준비 체크리스트 |
| 칩 버튼 | 위생교육·보건증·테라스 영업 | 사업자등록·영업신고·상권조사 |
| 발주 | 사용 | **숨김** (거래처가 아직 없다) |
| 상권 검색 | 사용 | 사용 (오히려 더 중요) |
| 법령 검색 | 사용 | 사용 |

검색·발주 로직 자체는 바뀌지 않는다. 진입점만 다르다.

### 체크리스트 공유

개업 준비 체크리스트는 `duties` 테이블을 그대로 쓴다.
기한이 없는 항목은 `due_date`가 null이고 `sort`로 순서만 표시한다.

```sql
due_date date,                 -- null 허용: 개업 준비는 기한이 없다
sort     int not null default 0
```

조회 시 `order by due_date nulls last, sort`.

### 전환의 의미

예비창업자는 **개업하면 떠난다.** 리텐션이 짧은 것이 약점이다.
다만 개업 후 자동으로 영업 중 모드로 넘어가므로, 오히려 **가장 자연스러운 신규 유입 경로**가
된다. 창업 준비 단계부터 쓰던 도구를 개업 후에도 계속 쓰게 하는 구조다.

### 구현 비용

- 테이블 추가 없음 (`app_users.status` 컬럼 하나)
- 화면 추가 없음 (홈 상단만 분기)
- 추가 작업: 개업 체크리스트 항목 10개 + 개업 FAQ 칩 10개를 손으로 작성 (2~3시간)

```
# ponytail: 상태 컬럼 하나 + 홈 화면 분기. 별도 테이블·화면 만들지 않는다.
```

### 테스트 방법

1. `preparing`으로 가입 → 홈에 개업 체크리스트가 뜨고 발주 메뉴가 숨는지
2. 설정에서 `open`으로 변경 → 과태료 체크리스트로 전환되는지
3. 두 모드 모두에서 상권·법령 검색이 동작하는지
